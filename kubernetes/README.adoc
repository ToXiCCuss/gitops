= GitOps Kubernetes
:sectnums:

== Setup

=== ArgoCD

----
helm repo add argo https://argoproj.github.io/argo-helm
helm install argocd argo/argo-cd -n argocd --values argocd-values.yaml --create-namespace
helm upgrade argocd argo/argo-cd -n argocd --values argocd-values.yaml
----

Each top-level folder is its own independently deployable ArgoCD app-of-apps
(`kube-app-<name>.yaml`), so a domain can be bootstrapped on its own via
`kubectl apply -f kubernetes/kube-app-<name>.yaml`. Inside a domain, the
manifests are split by *how* they are deployed:

----
kubernetes/<domain>/
  apps.yaml     the two child Applications below (the root app only reads this file)
  helm/         Applications that wrap Helm charts (operators, apps) - synced first, wave 0
  kubectl/      raw manifests (custom resources, Gateways, Secrets, ...) - synced second, wave 1
----

`<domain>-kubectl` waits until `<domain>-helm` is healthy, so operators and
their CRDs exist before the custom resources that need them - that is the
enforced ordering, no dry-run workarounds needed. Both are plain directory
sources without AVP; the `<path:...>` values in a Helm app are resolved later,
by the AVP Helm plugin of each child Application. Two rules follow from this:
a Helm app must not depend on anything that lives in the same domain's
`kubectl/` folder (it runs first), and a domain without Helm apps (`spring`)
simply has no `helm/` folder.

. infra (cert-manager, ClusterIssuer, Istio security policies, NetBird operator)
. monitoring (Prometheus, exporters, Istio dashboards)
. cicd (Harbor, Artifactory, Jenkins) — before `management`, see below
. management (Backstage, Microcks, Keycloak)
. kafka (Strimzi, Apicurio Registry, AKHQ)
. backup (Databasus)
. spring

`kube-vault.yaml` (Vault itself) and `kube-app-secrets.yaml` (the
`secrets/` folder: every raw Secret that AVP fills from Vault) sit at the
top level, not inside a domain folder, and are applied standalone before
`infra` — see the Deployment Guide below for why.

Sync-wave annotations (`argocd.argoproj.io/sync-wave`) additionally order
resources *within* `helm/` and within `kubectl/` (e.g. ClusterIssuer before
the NetworkResources), but not across domains — those orderings are
manual/documented instead:
`infra` must be healthy before the others (they all rely on its
ClusterIssuer and cert-manager), and `cicd` before `management` (Backstage
pulls its own image from Harbor). Istio itself and ArgoCD's own
installation are deliberately kept outside of GitOps (`istioctl` /
`helm install` per above), since both carry too much blast radius for
automated sync.

== Deployment Guide

=== 0. Prerequisites (outside of GitOps, done once manually)

. Kubernetes cluster reachable, `kubectl`/`helm` configured against it.
. Istio installed via `istioctl` (base + istiod + ingressgateway) — still
  needed for the remaining public apps (`keycloak.rjst.de`, `microcks.rjst.de`,
  `rjst.de`).
. NetBird self-hosted server running (per the
  https://docs.netbird.io/selfhosted/selfhosted-quickstart[quickstart script]),
  reachable at `proxy.rjst.de`, with its own Traefik reverse proxy.
. A NetBird personal access token (Management API scope) for the Kubernetes
  operator.


=== 1. Bootstrap ArgoCD

----
helm repo add argo https://argoproj.github.io/argo-helm
helm install argocd argo/argo-cd -n argocd --values argocd-values.yaml --create-namespace
----

=== 2. Deploy Vault standalone

----
kubectl apply -f kubernetes/kube-vault.yaml
----

Vault is deliberately *not* part of a domain app: everything that needs
AVP depends on Vault being up, unsealed and populated, so Vault is deployed
on its own first and populated (next step) before any Secret is rendered.

=== 3. Populate Vault secrets

The `avp-helm`/`avp` ArgoCD CMP plugins read secrets from Vault at sync time —
if a path is missing, that Application's manifests simply fail to render.
Populate these *before* applying the `secrets` app in step 4 (paths are
Vault KV v2, under `argocd/data/...`).

Three PowerShell scripts in `scripts/vault/` automate this against the Vault
from step 2 (port-forward it first: `kubectl port-forward -n vault svc/vault 8200:8200`):

----
# One-time only, right after step 2 deploys a fresh, uninitialized Vault:
.\scripts\vault\init-vault.ps1 -VaultAddr http://127.0.0.1:8200

# Generates the app-internal passwords, and prompts for the values that
# can't be generated (Hetzner/NetBird tokens, docker01 DB credentials,
# vault-backup secrets). Safe to re-run - blank answers never overwrite
# existing data. Writes nothing to disk.
.\scripts\vault\generate-secrets.ps1 -VaultAddr http://127.0.0.1:8200 -VaultToken <root-token-from-init>
----

[cols="1,2"]
|===
|Vault path |Keys

|`argocd/data/hetzner`
|`token` (Hetzner Cloud API token, DNS read/write)

|`argocd/data/netbird`
|`api_key` (NetBird Management API personal access token)

|`argocd/data/prometheus`
|`password` (Grafana admin password)

|`argocd/data/harbor`
|`admin.password`, `database.username`, `database.password`

|`argocd/data/jenkins`
|`password` (Jenkins admin password)

|`argocd/data/keycloak`
|`postgresql.username`, `postgresql.password`

|`argocd/data/microcks`
|`username`, `password` (MongoDB connection on `docker01`)
|===

NOTE: Everything is in Vault except Vault's own unseal keys. Those aren't in
the table above and aren't stored in Vault at all - they're circular on a *first* install (Vault must already
be unsealed for AVP to read them back out of it). `init-vault.ps1` above
creates them via `vault operator init`, unseals Vault, and applies the
`vault-unsealer-config` Secret straight into the cluster with `kubectl`
(bypassing AVP for that one bootstrap secret). The root token and unseal
keys are only printed to the console, once - it waits for Enter so you can
copy them into your password manager. They are not saved anywhere else.

==== Kubernetes auth (required)

Run `scripts/vault/configure-vault-auth.ps1` once, after `init-vault.ps1`
(it needs `kubectl` against the cluster and a Vault token with admin rights,
e.g. the root token from init). It sets up everything that lets workloads
authenticate to Vault directly with their own ServiceAccount:

* Enables Vault's `kubernetes` auth method and configures it for this cluster.
* Creates the `argocd`, `jenkins`, `dev`, `prod` and `backup` KV v2 engines.
* Writes the policies and auth roles for ArgoCD, Jenkins, the Spring apps
  (`dev`/`prod` namespaces) and the Vault backup CronJob.

The `argocd` role matters most: ArgoCD's AVP plugin itself logs in to Vault
through it (`AVP_AUTH_TYPE=k8s`, role `argocd`, see `argocd-values.yaml`), so
nothing that uses AVP - including the `secrets` app - renders without it.

The Vault backup CronJob (`backup/kubectl/kube-vault-backup.yaml`) depends on it: it
logs in through the `vault_backup` role this script creates, so the backup
fails without it. Jenkins and Spring don't read from Vault at runtime yet;
wiring them up (Vault Agent injector, Spring Cloud Vault, etc.) is a separate,
later step, app by app.

----
.\scripts\vault\configure-vault-auth.ps1 -VaultAddr http://127.0.0.1:8200 -VaultToken <token>
----

==== Vault backups

A `CronJob` (`kubernetes/backup/kubectl/kube-vault-backup.yaml`, daily at 03:00)
takes a Raft snapshot and pushes it to the same restic/pCloud repository
your old Linux cron job used (`rclone:pCloud:/Backups/vault_pb`) — it
replaces that cron entirely; remove it from the old host's crontab
yourself, this repo can't reach that machine. It authenticates to Vault
with its own ServiceAccount (`vault-backup-sa` in the `backup` namespace,
Kubernetes auth, no static token), and reads the restic password + your
`rclone.conf` (with the pCloud remote) from Vault at
`backup/data/vault-backup` — set those via `generate-secrets.ps1`'s
"Vault backup" prompt. `scripts/vault/vault_restore.sh` still works
unchanged for restores, since it just reads from the same restic repo.

=== 4. Deploy the secrets, then the domains, in this order

----
kubectl apply -f kubernetes/kube-app-secrets.yaml     # 0. renders the Secrets from Vault via AVP, must be healthy before infra
kubectl apply -f kubernetes/kube-app-infra.yaml       # 1. cert-manager, ClusterIssuer, NetBird operator
kubectl apply -f kubernetes/kube-app-monitoring.yaml  # 2. needed before kafka (PodMonitor CRDs)
kubectl apply -f kubernetes/kube-app-cicd.yaml        # 3. needed before management (Backstage pulls its image from Harbor)
kubectl apply -f kubernetes/kube-app-kafka.yaml       # 4. onwards: order doesn't matter, all only need infra
kubectl apply -f kubernetes/kube-app-management.yaml
kubectl apply -f kubernetes/kube-app-backup.yaml
kubectl apply -f kubernetes/kube-app-spring.yaml
----

Why the secrets are a separate app that comes first: some Helm apps need
their Secret at start (the NetBird operator needs `netbird-mgmt-api-key`),
but `helm/` runs before `kubectl/`, so those Secrets can't wait for the
domain's `kubectl/` folder. `secrets` holds them (plus the namespaces they live
in) and is the only place that runs the AVP plugin, so *every* Secret that is
filled from Vault lives there. Don't set the plugin on an app whose files
contain no `<path` / `avp.kubernetes.io` marker: the plugin's discovery check
finds nothing and ArgoCD fails with "could not find cmp-server plugin".
Never put the AVP plugin on a `helm/` app: it would resolve every `<path:...>` in the child Applications'
`HELM_VALUES` and write those passwords in plain text into the Application
objects.

Watch `infra` reach Healthy in the ArgoCD UI/CLI before applying the rest —
nothing else will work without its ClusterIssuer and cert-manager.

=== 5. NetBird configuration

What lives in Git, and what doesn't:

* *In Git, via the NetBird operator* (`kubernetes/infra/kubectl/kube-netbird-access.yaml`,
  applied with `infra`): the groups. `k8s-admins` (peers that may reach every
  app), `kubernetes-services` (every `NetworkResource` is in it), and per app a
  destination group `k8s-<app>` and a user group `<app>-users`.
* *By hand in the dashboard* (no Terraform for now; `terraform/` is optional and
  not needed for this):
  . `DNS > Zones > Add Zone`: name and domain `k8sdev.rjst.de` (a separate internal
    zone: `proxy.rjst.de` is the NetBird host's own public domain and must not
    be shadowed; a subdomain of `rjst.de` so Let's Encrypt DNS-01 can issue for
    it). *Distribution Groups*: `k8s-admins` and every `<app>-users` (only peers
    in these groups resolve the records; the zone is not a security boundary,
    the policies are). The zone must exist before the `NetworkRouter` syncs.
  . Records in that zone: the operator creates `<service>.<namespace>.k8sdev.rjst.de`
    for every `NetworkResource`. Add a CNAME per app to that name, e.g.
    `vault.k8sdev.rjst.de` -> `gw-vault.istio-internal.k8sdev.rjst.de`.
  . `Access Control > Policies`, all TCP 443, one-way:
    `k8s-admins` -> `kubernetes-services` (every app), and per app
    `<app>-users` -> `k8s-<app>` (e.g. `vault-users` -> `k8s-vault`).
    NetBird is deny-by-default and the operator writes no policies (its
    `NBPolicy` resource creates nothing for `NetworkResource`s, so it is
    deliberately not used).
  . `Peers`: put each peer/user into `k8s-admins` and/or the matching
    `<app>-users`. Nothing is reachable until a peer is in a group with a policy.
  . The group formerly called `kubernetes-clients` is renamed to `k8s-admins` by
    the operator (same group ID, so existing peers and policies stay).
* Guide this follows: https://docs.netbird.io/use-cases/kubernetes/route-to-a-kubernetes-service[Route to a Kubernetes service].
  The router runs a single routing peer (`workloadOverride.replicas: 1`,
  single-node cluster); raise it to 3+ for failover.
* *Reverse proxy* (`<app>.proxy.rjst.de -> <service>.<namespace>.k8sdev.rjst.de:<port>`,
  see the port table below): still manual, on the NetBird host. Do *not* create
  these as services with the Terraform provider (v0.0.10): it can't mark a
  service as private/NetBird-only, so they'd be reachable from the internet.

NOTE: for now only Vault is exposed (through `istio-internal`, see below).
The direct `NetworkResource`s for ArgoCD and Vault are parked in
`kubernetes/parked/` (nothing syncs that folder). The other apps'
`NetworkResource`s sit in domains that aren't applied yet and still use the
direct `<service>.<namespace>.k8sdev.rjst.de:<port>` model; move them to the
per-app gateway pattern when you deploy those domains.

Once `infra` is healthy, each app's `NetworkResource` (ArgoCD, Vault, Grafana,
Harbor, Jenkins, Backstage, AKHQ, Apicurio Registry, Databasus) shows up under
the zone as `<service>.<namespace>.k8sdev.rjst.de`.

==== HTTPS entry for internal apps (`istio-internal`)

Apps are reached as `https://<app>.k8sdev.rjst.de` (port 443, Let's Encrypt
wildcard `*.k8sdev.rjst.de` via the `letsencrypt` ClusterIssuer, DNS-01 at
Hetzner). `istio-internal-gateway` (`infra/helm`) is a second Istio ingress
gateway, ClusterIP only - unlike the public `istio-ingressgateway`, nothing
outside the cluster can reach it except through the NetBird routing peer.
NetBird separates access per destination, not per hostname, so every app gets
its own Service, its own listener port on the gateway and its own
`NetworkResource` (`infra/kubectl/kube-istio-internal.yaml`). Each listener
only accepts that app's hostname, so per-app groups stay meaningful. Vault is
the first app there. The earlier direct `NetworkResource` on port 8200 is parked
in `kubernetes/parked/`, so the HTTPS route is the only way in.

=== 6. Verify

----
kubectl get applications -n argocd
kubectl get clusterissuer
kubectl get certificates -A
kubectl get networkresources -A
----

All `Application` rows should show `Synced`/`Healthy`, and each
`NetworkResource` should have a matching entry in the NetBird dashboard
under the `k8sdev.rjst.de` zone.
