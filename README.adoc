= GitOps

Infrastructure as code for the two servers (a Docker host and a k3s node).

[cols="1,3"]
|===
|Folder |Content

|`ansible/`
|Host setup with Ansible: base system, firewall (UFW), Docker, NetBird, k3s and its registry mirror, database servers, node exporter. Secrets in an ansible-vault file.

|`docker/`
|One Docker Compose project per service on the Docker host (Backrest, Databasus, SeaweedFS, offsite sync, ...), deployed by `scripts/docker/deploy.sh`. Images are pinned by digest and updated by Renovate.

|`kubernetes/`
|ArgoCD app-of-apps, one folder per domain (infra, monitoring, cicd, management, kafka, spring).

|`scripts/`
|Helper scripts: Ansible secrets, backup host setup, Vault (PowerShell), database administration, Linux benchmarks.
|===

== Ansible

Run everything in this section from the `ansible/` folder.

=== Install Ansible

Install Ansible and Git on Debian:

[source,bash]
----
sudo apt update
sudo apt install -y ansible git && git clone https://github.com/ToXiCCuss/gitops.git
----

Then switch to the repository and install the required collections:

[source,bash]
----
cd gitops/ansible
ansible-galaxy collection install -r requirements.yml
----

=== Dry Run

Before the actual execution, check the playbook in check mode. This does not make any changes:

[source,bash]
----
ansible-playbook -i inventory.ini site.yml --check --diff
----

=== Apply Changes

If the dry run completes without unexpected errors, run the playbook:

[source,bash]
----
ansible-playbook -i inventory.ini site.yml
----

=== Firewall

The role `firewall` runs on the hosts in `firewall_hosts` (`group_vars/all/main.yml`). It allows the ports listed in
`host_config.<host>.firewall_rules`, denies all other incoming traffic and enables UFW. Each rule needs `port`, `proto` and
`comment`, `from_ip` is optional (default: any):

[source,yaml]
----
host_config:
  docker01:
    firewall_rules:
      - { port: 8333, proto: tcp, from_ip: 172.16.0.0/12, comment: "SeaweedFS S3 from the Docker networks" }
----

* UFW only filters traffic to host processes (sshd, PostgreSQL, node_exporter, the NetBird client). Ports published by Docker
  bypass it (FORWARD chain), a rule here neither opens nor closes them.
* There is no UFW rule for SSH: `docker01` is reached through NetBird and port 22 is closed to the Internet.
* The role never removes rules. A rule that is no longer wanted is removed by hand once (`ufw delete ...`) after it is
  deleted from `firewall_rules`.
* Run only this role with `--tags firewall`. Do a dry run (`ansible-playbook -i inventory.ini site.yml --tags firewall --check --diff`)
  before the first real run and compare it with `ufw status verbose` on the host. Adding a comment to an existing rule counts as a
  change once.

=== k3s

The role `k3s` runs on the hosts in `k3s_hosts` (`group_vars/all/main.yml`). It installs the pinned `k3s_version` with the
official install script, writes `/etc/rancher/k3s/config.yaml` and keeps the service running. The server flags are the keys of
`host_config.<host>.k3s_config` (`node-ip` defaults to the primary IPv4 address), the registry mirror stays in the role `k3s_registries`.

* Change a flag: edit `k3s_config`, run `ansible-playbook -i inventory.ini site.yml --tags k3s`. k3s is restarted once (the API
  server is gone for a moment, the pods keep running).
* Upgrade: change `k3s_version` (a release from https://github.com/k3s-io/k3s/releases) and run the same command. Do a dry run
  (`--tags k3s --check --diff`) first.
* A node that was installed with the flags in the systemd unit is migrated by the first run: the install script rewrites the
  unit without flags, they move to `config.yaml`, and k3s restarts once.
* The cluster uses embedded etcd (`cluster-init`). Its snapshots are only local (`/var/lib/rancher/k3s/server/db/snapshots`),
  they are not part of the backups yet.

=== Secrets (ansible-vault)

Secrets do *not* live in `group_vars/all/main.yml` but in
`group_vars/all/secrets.yml`. That file is encrypted with `ansible-vault`
(AES256) and *is committed to Git* in encrypted form. Ansible loads it
automatically, so no playbook or role needs changing.

Managed secrets:

[cols="2,2,3"]
|===
|Variable |Used by |Source

|`netbird_setup_key`
|`roles/netbird`
|NetBird dashboard -> Setup Keys

|`k3s_registries_harbor_password`
|`roles/k3s_registries`
|Harbor account / robot account

|===

==== Per-host values

Values are stored per scope in the nested dict `vault_secrets`:

[source,yaml]
----
vault_secrets:
  all:                                        # fallback for every host
    k3s_registries_harbor_password: ...
  docker01:                                   # overrides "all" on that host
    netbird_setup_key: ...
  k8sdev01:
    netbird_setup_key: ...
----

The very same layering exists in plain text for *non-secret* per-host
settings, in `host_config` in `group_vars/all/main.yml`:

[source,yaml]
----
host_config:
  all: {}
  docker01:
    some_setting: "value"
----

`group_vars/all/main.yml` merges the `all` layer with the current host's layer
once (`_secrets` / `_config`) and resolves each variable in this order:

. `vault_secrets[<ansible_hostname>][<name>]` - host specific
. `vault_secrets["all"][<name>]` - shared by every host
. `""` - the role's `assert` task reports the missing value

NOTE: *Why not `host_vars/`?* `inventory.ini` only knows `localhost`, and Ansible
resolves `host_vars/` by _inventory_ name - `host_vars/docker01.yml` would
never be loaded. `ansible_hostname` is a fact and holds the real hostname,
which is also what the `*_hosts` gates compare against.

Note that this is organisation, not isolation: the encrypted file is in Git and
every host with `.vault_pass` can decrypt *all* scopes. Real per-host
separation would need several vault IDs (`vault_identity_list`).

==== First setup on a host

[source,bash]
----
../scripts/ansible/setup-secrets.sh
----

Without arguments the script uses *this machine's own short hostname* as the
scope (`hostname -s`, falling back to `uname -n`) - that is exactly the key
`ansible_hostname` resolves to later, since the playbook runs locally on each
host. It then asks for each secret; input is not echoed. It writes the
encrypted `group_vars/all/secrets.yml` and creates the vault password file
`ansible/.vault_pass` (`chmod 600`, gitignored). On a fresh setup it can
generate a random vault password - *store it in your password manager*,
otherwise the committed `secrets.yml` is unreadable everywhere else.

Afterwards commit the encrypted file:

[source,bash]
----
git add ansible/group_vars/all/secrets.yml && git commit -m "Update Ansible vault secrets"
----

==== Additional host (secrets.yml already in Git)

Only the password file is missing there:

[source,bash]
----
../scripts/ansible/setup-secrets.sh --password
----

The script asks for the vault password and verifies it against the checked-out
`secrets.yml` before writing `.vault_pass`.

==== Day-to-day

[source,bash]
----
../scripts/ansible/setup-secrets.sh                    # THIS host (auto-detected)
../scripts/ansible/setup-secrets.sh --scope all        # shared by every host
../scripts/ansible/setup-secrets.sh --scope docker01   # another host
../scripts/ansible/setup-secrets.sh --view             # show the decrypted content
../scripts/ansible/setup-secrets.sh --edit             # raw edit in $EDITOR
../scripts/ansible/setup-secrets.sh --rekey            # rotate the vault password
----

At each prompt: Enter keeps the current value, `-` removes the entry. A removed
host entry falls back to the value from scope `all`. Scopes that run empty are
dropped from the file.

The script prints the scope it is about to write to, and warns when the detected
hostname appears in none of the `*_hosts` lists in `main.yml` - usually a sign
that the host has not been wired into the playbook yet.

==== Adding a new secret

. Add the variable with an empty default to the role's `defaults/main.yml`.
. Append its name to `SECRET_NAMES` and a description to `SECRET_HINTS` in
  `scripts/ansible/setup-secrets.sh`.
. Add the host -> all -> `""` look-up to the _Secrets_ block in
  `group_vars/all/main.yml` (copy an existing one).
. Run the script - existing values are preserved.

NOTE: `ansible.cfg` sets `vault_password_file = .vault_pass`. If that file
is missing, _every_ `ansible-playbook` run aborts with
`The vault password file .vault_pass was not found` - run the script first.
Tasks that use secrets already have `no_log: true`, so the values do not show
up in the output or in `--check --diff`.

== Docker

=== Deploy

The Compose projects of `docker/` are deployed with one script, there is no management UI. It is idempotent: a project is only
recreated when its compose file or its environment changed.

----
sudo scripts/docker/deploy.sh                       # all projects, in a fixed order
sudo scripts/docker/deploy.sh backrest vault-backup # only these
sudo scripts/docker/deploy.sh --pull seaweedfs      # git pull --ff-only first
sudo scripts/docker/deploy.sh --list
----

`deploy.sh` never removes anything. To take a project down (also one that was already deleted from `docker/`) use `undeploy.sh`. It needs
at least one project name, asks before it acts and removes only the containers and networks, the data and the named volumes stay:

----
sudo scripts/docker/undeploy.sh uptimeKuma
sudo scripts/docker/undeploy.sh --yes backrest databasus   # without the question
----

`cleanup.sh` shows what Docker keeps without using it (dry run) and with `--apply` removes only the safe part: unused images without a tag
and the build cache. The images of `docker/` are pinned by digest and have no tag, so the old versions that Renovate leaves behind
appear as `repository:<none>`. Images with a tag and no container, volumes, stopped containers and networks are only listed. Volumes hold data, `netbird-rollback/*` are the rollback points of `netbird_upgrade.sh` and Pelican creates its
own networks and containers.

----
sudo scripts/docker/cleanup.sh            # dry run
sudo scripts/docker/cleanup.sh --apply
----

The secrets of a project are in `docker/<project>/override.env`. The file is *not* in Git (`.gitignore`), the variables a project needs are
named in `docker/<project>/override.env.example` (`NAME=` is required, `#NAME=` is optional). `default.env` lists all variables of
a project and the compose file reads `default.env` first and `override.env` second. `deploy.sh` checks the required variables before it
touches a container and lists what is missing. Projects with secrets: `backrest`, `offsite-sync`, `vault-backup`.

New or changed secret:

. Edit `docker/<project>/override.env` on the server (a new variable in the example file after a `git pull` is reported the same way).
. `sudo scripts/docker/deploy.sh <project>`: Compose sees the changed environment and recreates the container within seconds.
  The data lives in folders on the host and stays.
. The S3 keys of `backrest`, `offsite-sync` and `vault-backup` do not need to be copied: `setup-backup-host.sh` writes them into the
  `override.env` files (`s3.json` is the source of truth). After new keys run it and deploy these projects again.

NetBird is not part of this: it runs from its own folder (`/root/netbird`, created by the NetBird installer, with secrets), see Setup NetBird backup.

Move from the old management UI (once): `git pull`, run `setup-backup-host.sh` (it writes the S3 keys), fill the rest of the `override.env`
files, then deploy project by project with `--adopt`. That removes the existing container of the same name that belongs to another
Compose project (a short interruption, the data stays) and creates it again. Finally stop and remove the old UI container.

=== Backups

All backups of the Docker host go to a local SeaweedFS S3 first and from there once a night to pCloud.
Every service is its own Compose project (deployed by `scripts/docker/deploy.sh`), the details are in the
`Setup ...` sections below.

[source,mermaid]
----
flowchart LR
  vault[("Vault (Kubernetes)")]
  subgraph host["Docker host"]
    vault -->|"snapshot API, periodic token"| vaultbackup["vault-backup (restic)"]
    keys["Key files"] -->|read-only| backrest["Backrest (restic)"]
    pg[("PostgreSQL")] --> databasus["Databasus (pg_dump)"]
    backrest -->|bucket backups| s3[("SeaweedFS S3")]
    databasus -->|bucket databases| s3
    vaultbackup -->|bucket vault| s3
    netbird["NetBird server (netbird_backup.sh, restic)"] -->|bucket netbird| s3
    s3 -->|read-only identity| sync["offsite-sync (rclone, 05:00 UTC)"]
  end
  sync -->|"rclone sync, deleted files go to Backups-deleted"| pcloud(["pCloud"])
----

[cols="1,1,2"]
|===
|Service |Task |Notes

|SeaweedFS |Local S3 staging |One identity per service, the offsite sync can only read
|Backrest |Backs up a few static key files, checks the repositories and browses and restores snapshots |restic, repository `backups/docker`. Also used to check and restore the Vault and NetBird repositories
|Databasus |Logical PostgreSQL backups (`pg_dump`) |bucket `databases`
|vault-backup |Daily Raft snapshot of Vault |Periodic token that may only read the snapshot, bucket `vault`, repository `vault/raft`, keeps its own retention
|NetBird backup |Config and database of the self-hosted NetBird server (`scripts/netbird/`) |bucket `netbird`, repository `netbird/restic`, keeps its own retention
|Offsite sync |Copies the whole S3 to pCloud and verifies the copy |Keeps deleted or overwritten files 30 days in `Backups-deleted`
|===

Everything writes to the S3 only, pCloud is written by the offsite sync alone. Not covered:
the PVCs of the Kubernetes apps and MariaDB. MongoDB is not operated (`mongodb_hosts` is empty); its
scripts in `scripts/mongodb/backup/` are kept, but they still write directly to pCloud.

==== Discord alerts

Failed backups are reported to a Discord channel through a webhook. Only failures are posted, a run that succeeds is silent. A job that
does not run at all (container stopped, host down) sends nothing, so look at `docker ps` now and then.

. Create a channel only for alerts (not the chat of a game server): *Edit Channel > Integrations > Webhooks > New Webhook*, copy the URL.
. The URL is a secret, whoever knows it can post to the channel. Keep it out of Git.
. Enter it where the job runs:
+
[cols="1,3"]
|===
|Job |Where
|`offsite-sync`, `vault-backup` |`DISCORD_WEBHOOK_URL` in `docker/<project>/override.env`, then `sudo scripts/docker/deploy.sh <project>`
|`netbird_backup.sh` |`sudo ./netbird_backup_setup.sh --discord-webhook <url>` (writes it to `/etc/netbird-backup.cred`)
|Databasus |In the UI add a Discord notifier with the URL and select it for every database (failed backups)
|Backrest |In the UI add a Discord hook to the repositories and the plan, condition `CONDITION_ANY_ERROR`
|===
. Test the webhook, a message must appear in the channel:
+
----
curl -H 'Content-Type: application/json' -d '{"content":"test"}' '<webhook url>'
docker exec offsite-sync sh -c 'wget -q -O /dev/null --header "Content-Type: application/json" --post-data "{\"content\":\"offsite-sync test\"}" "$DISCORD_WEBHOOK_URL"'
----

An old `PUSH_URL` in an `override.env` or in `/etc/netbird-backup.cred` is ignored now, delete the line. Uptime Kuma is no longer part
of the repository: stop it once with `sudo scripts/docker/undeploy.sh uptimeKuma` (if that finds nothing, the container was created by the old management UI: `docker rm -f uptime-kuma`), its data stays in `/root/docker/uptime-kuma` until you delete it.

==== Setting it up, in this order

. If there is no pCloud remote yet, get a token: on a machine with a browser and rclone run
  `rclone authorize "pcloud"` and keep the printed token JSON. The setup script asks for it and
  creates the remote `pCloud` in `/root/.config/rclone/rclone.conf`. An existing remote is reused.
. Create a Discord webhook for the alerts, see <<Discord alerts>>.
. Prepare the host. It creates the data directories, installs `rclone.conf`, checks pCloud and
  generates the S3 identities and keys (`/root/backup-credentials.env`). The bucket step reports
  that S3 is not reachable yet, that is expected:
+
----
sudo scripts/docker/setup-backup-host.sh
----
. Deploy the `seaweedfs` project: `sudo scripts/docker/deploy.sh seaweedfs`.
. Run the script again, now it creates the buckets `backups`, `databases`, `vault`, `pelican` and `netbird`. SeaweedFS is restarted by the
  script when identities changed. The script also writes the S3 keys into `docker/backrest/override.env`,
  `docker/offsite-sync/override.env` and `docker/vault-backup/override.env`.
. Fill in what is still missing in these files (`deploy.sh` stops and lists it):
+
[cols="1,3"]
|===
|Project |Still to enter in `override.env`

|`backrest`
|nothing required, `RESTIC_PASSWORD` is optional

|`offsite-sync`
|nothing required, `DISCORD_WEBHOOK_URL` is optional

|`vault-backup`
|`VAULT_TOKEN` (see below), `RESTIC_PASSWORD` (the password of the Vault repository), optional `DISCORD_WEBHOOK_URL`
|===

`VAULT_TOKEN` is a periodic token that may only read the Raft snapshot. Create it once with the root token,
the script prints it once:

----
.\scripts\vault\create-snapshot-token.ps1 -VaultAddr http://127.0.0.1:8200 -VaultToken <root-token>
----

The Docker host must reach `https://vault.k8sdev.rjst.de`: `docker01` is a NetBird peer, put it into the
group `vault-users` (the policy `vault-users` -> `k8s-vault` exists, see NetBird configuration).

. Deploy them: `sudo scripts/docker/deploy.sh backrest databasus vault-backup offsite-sync`.
. Configure the services in their UIs (see the sections below): Backrest (admin user, repository,
  plan for the key files, a second repository `s3:<S3_ENDPOINT>/vault/raft` with the restic
  password of the Vault backup, only to check and restore) and Databasus (S3 storage with the
  `databasus` keys, databases, schedule). Databasus is the only place that needs the `databasus` keys.
. Delete `/root/backup-credentials.env` and store the restic password and `rclone.conf` in your
  password manager. Without them the pCloud backups cannot be read after a total loss.

Backrest (`9898`), Databasus (`4005`) and the S3 port (`8333`) are published on all interfaces
of the host. Restrict them to NetBird with a host firewall and allow them for your peers with
NetBird policies. The backups should run before the sync, so schedule them between 01:00 and 03:00.

==== Test the restore

A backup that was never restored is not a backup. After the first nightly sync, and then once per
quarter, restore a volume or a database from *pCloud*, not from the local S3: add the pCloud
repository (`rclone:pCloud:/Backups/s3/backups/docker`) in Backrest as an additional repository and
restore into `/restore`.

=== Restore

Keep these in the password manager, nothing can be read without them and they are not on the servers:

* the restic passwords of the repositories `docker` (Backrest), `vault` (project `vault-backup`) and `netbird` (`/root/restic`)
* the `rclone.conf` of pCloud (the token)
* the Vault unseal keys and the root token (printed once by `init-vault.ps1`) and the Ansible vault password (`ansible/.vault_pass`)

[cols="1,2"]
|===
|Data |Restore with

|Secrets and key files (the `override.env` files, `rclone.conf`, `seaweedfs-s3.json`, `secret.key`) |Backrest, repository `docker` (below)
|PostgreSQL |Databasus (below)
|Vault |`scripts/vault/vault_restore.sh` (below)
|NetBird server |`netbird_restore.sh` (below)
|Pelican game servers |Pelican Panel, or unpack the plain `.tar.gz` by hand (below)
|The whole S3 is lost |restic directly from pCloud (below)

==== Key files

. Backrest: repository `docker` -> snapshots -> browse the snapshot, select the file -> restore to a *new* folder below `/restore`,
  e.g. `/restore/test1` (`/restore` is the only writable path, `/root/docker/backrest/restore` on the host). Backrest refuses a target that
  exists already (`target directory "/restore" already exists`), so use a new name each time or delete the old folder. The restored
  files hold secrets in plain text, delete the folder afterwards.
. Copy the file back to its place (`/root/gitops/docker/<project>/override.env`, `/root/docker/seaweedfs-s3.json`,
  `/root/docker/backrest/rclone/rclone.conf`, `/root/docker/offsite-sync/rclone/rclone.conf`, `/root/docker/databasus/secret.key`),
  check the owner and mode (`override.env` `600`) and deploy the project with `deploy.sh`.

After a total loss restore `seaweedfs-s3.json` first or create the identities again with `setup-backup-host.sh`.
The key files are also in the repository `docker` on pCloud, see the last section.

==== PostgreSQL

. Databasus: select the database, then the backup and restore it. Restore into a scratch database first to look at the result.
. On a new server: run the Ansible role `postgresql` (PostgreSQL 18 with `pg_cron` and `pg_partman`), create the database with
  `db_create.sh <name>` and the backup role with `backup_user_create.sh`, then restore the dump with Databasus.
. Databasus itself: its configuration (databases, storage, schedules) is not backed up, set it up again as in Setup Databasus.
  The file `secret.key` is backed up (repository `docker`): put it back into `/root/docker/databasus/` *before* the first start, then
  the encrypted backups can be restored.
. Without Databasus (https://databasus.com/how-to-recover-without-databasus/): take three things from the bucket `databases` (or from
  pCloud, `Backups/s3/databases/`) and the key file. The backup file `<database>-<timestamp>-<backup id>`, its `.metadata` file (salt and
  initialisation vector) and `secret.key`. The backups are AES-256-GCM encrypted. Decrypt them with the Python script of that page
  (`pip install pycryptodome`, enter the paths and the key in `decrypt_backup(...)`), the result is `decrypted_<file>`. Then restore it:
+
----
pg_restore -h <host> -U <user> -d <database> decrypted_<file>
----
+
The metadata file must belong to the backup file, a wrong key or a damaged file makes the decryption fail. Keep `secret.key` in the
password manager as well: without it the dumps are unreadable.

==== Vault

. Vault runs (Argo, `kube-vault.yaml`) and is initialised and unsealed (`init-vault.ps1` on a fresh Vault).
. On a host with the `vault` CLI: `VAULT_ADDR` and `VAULT_TOKEN` (root token) set, and `/etc/vault-backup.cred` with the lines
  `S3_ENDPOINT=...`, `AWS_ACCESS_KEY_ID=...` and `AWS_SECRET_ACCESS_KEY=...` (identity `vault` or `backrest`).
. Put the restic password of the Vault repository into a file and run the script, it lists the snapshots and asks which one to restore:
+
----
sudo RESTIC_PASSWORD_FILE=/root/restic-vault scripts/vault/vault_restore.sh
----

A snapshot replaces all data of Vault. After restoring a snapshot of another cluster the unseal keys of the backed up
cluster apply, and the restore may need `-force`. Snapshots from before the move are in `rclone:pCloud:/Backups/vault_pb`
(set `RESTIC_REPOSITORY`).

==== NetBird

`netbird_restore.sh` works on the original server and on a new one (Docker and Compose installed, the same domain pointing to it,
TCP 80 and 443 and UDP 3478 open). It needs `/etc/netbird-backup.cred` with the S3 keys of the identity `netbird` and
`/root/restic`, both are written by `netbird_backup_setup.sh`. It lists the snapshots and restores the selected one:

----
sudo netbird_restore.sh
----

After a failed upgrade `netbird_rollback.sh` goes back to the rollback point made by `netbird_upgrade.sh`.

==== Pelican game servers

Panel -> server -> Backups -> Restore. Pelican fetches the backup from the bucket `pelican`, the Wings must reach port 8333 of the S3.
The Panel and the Wings configuration are not backed up on purpose (see Setup Pelican). Without the Panel unpack the `.tar.gz` of the server by hand.

==== The S3 is lost (restore from pCloud)

The offsite sync keeps a copy of every bucket in `pCloud:/Backups/s3/<bucket>/`. The restic repositories can be read from there
directly, without the S3, with the `rclone.conf` and the restic password:

----
restic -r rclone:pCloud:/Backups/s3/backups/docker snapshots
restic -r rclone:pCloud:/Backups/s3/vault/raft restore latest --target /restore/vault
restic -r rclone:pCloud:/Backups/s3/netbird/restic restore latest --target /restore/netbird
----

In Backrest the repository `pcloud` does the same in the UI. To fill a new SeaweedFS again, run the nightly sync the other way
round: `rclone sync pCloud:/Backups/s3 SEAWEED:` (with an S3 remote named `SEAWEED` and the admin key).

=== Setup Backrest

Backrest is the web UI for restic on the Docker host. It backs up a few static key files read-only to the local
SeaweedFS S3, checks the repositories and is used to browse and restore snapshots. It reaches the S3 as
`host.docker.internal` (set in the compose file), the firewall must allow the Docker network to reach port 8333
(see Setup Databasus).

* Secrets are in `docker/backrest/override.env` (`setup-backup-host.sh` writes the S3 keys of the identity `backrest`), `default.env` lists all variables.
  Besides the S3 keys it holds the restic passwords of the repositories (`RESTIC_PASSWORD_DOCKER`, `RESTIC_PASSWORD_VAULT`) and optionally `DISCORD_WEBHOOK_URL`
* The configuration (repositories, schedules, plan, hooks) is in Git: `docker/backrest/config.template.json`. `docker/backrest/pre-deploy.sh`
  (run by `deploy.sh`) renders `/root/docker/backrest/config/config.json` from it, fills the `${NAME}` placeholders from the env files, keeps the users and
  restarts Backrest. *Change repositories, plans and hooks in the template, not in the UI:* the next deploy overwrites UI changes. Check a change first
  with `bash docker/backrest/pre-deploy.sh /tmp/config.test.json` (writes only that file, restarts nothing)
* If Backrest does not answer on port 9898 after the restart (for example because it refuses the new file), `pre-deploy.sh` puts the previous file back
  (saved as `config.json.before-deploy`), restarts Backrest again and fails, so `deploy.sh` shows `backrest: pre-deploy.sh failed`. Read the reason with
  `docker logs backrest`; the log of the failed start is also printed
* Deploy the project with `sudo scripts/docker/deploy.sh backrest`, open `http://<docker-host>:9898` and create the admin user *at once*
  (Backrest has no login until then, and Hooks run shell commands). The users stay across deploys
* The pCloud remote (`rclone.conf`) for restoring from pCloud is created and installed to `/root/docker/backrest/rclone/rclone.conf` by `setup-backup-host.sh`
* Restore only into `/restore`, then move the data into place
* Store the restic passwords and `rclone.conf` outside the server as well (password manager)

=== Setup Databasus

Databasus makes the logical backups (`pg_dump`) of the PostgreSQL databases and writes them to the bucket
`databases` of the local SeaweedFS S3. PostgreSQL 18 runs directly on the Docker host (Ansible role `postgresql`),
Databasus reaches it as `host.docker.internal`, which the compose file points to the host.

==== On the Docker host

. Create the login role once. It gets `pg_read_all_data` (SELECT on all tables, views and sequences in all
  databases and schemas, also later ones) and `CONNECT` on every existing database. The `ro` role of
  `user_create.sh` is not enough, it only sees the `public` schema of one database and would miss e.g. the
  `partman` schema. The script prints the password once, an existing role keeps its password (`reset` sets a new one):
+
----
sudo scripts/postgresql/backup_user_create.sh
----
. `CONNECT` is needed because `db_create.sh` revokes it from `PUBLIC` and `pg_read_all_data` does not include it.
  `db_create.sh` grants it on every new database. Run the script above again for databases created in another way
  (the error otherwise is `permission denied for database`).
. The containers of the Docker network must reach PostgreSQL (5432) and the S3 (8333) of the host. The firewall blocks
  that by default (the test below times out). The Ansible role `firewall` allows both from `172.16.0.0/12`, see
  <<Firewall>>. Test it from a container, `open` is the right answer:
+
----
docker run --rm --add-host=host.docker.internal:host-gateway alpine nc -zv -w 5 host.docker.internal 5432
docker run --rm --add-host=host.docker.internal:host-gateway alpine nc -zv -w 5 host.docker.internal 8333
----
. Deploy the project with `sudo scripts/docker/deploy.sh databasus` (the container is recreated for the host entry).

=== Setup SeaweedFS

SeaweedFS is the local S3 staging for all backups. Access is controlled by separate identities in
`/root/docker/seaweedfs-s3.json` (mounted read-only, contains secrets, never in git):

[cols="1,1,1"]
|===
|Identity |Bucket |Rights

|`admin` |all |Admin (only for you, not used by containers)
|`backrest` |`backups`, `vault`, `netbird` |Read, Write, List
|`databasus` |`databases` |Read, Write, List
|`vault` |`vault` |Read, Write, List
|`pelican` |`pelican` |Read, Write, List (for the S3 backups of Pelican)
|`netbird` |`netbird` |Read, Write, List (for `netbird_backup.sh`)
|`offsite-sync` |all |Read, List (cannot change anything)

* Run `scripts/docker/setup-backup-host.sh` *before* deploying: it prepares the host and creates the identities
(`/root/backup-credentials.env`). It is idempotent: existing identities and their keys are never changed, only
missing identities and buckets are added (needs `jq`). To add a service later, add an `ensure_identity` line and the bucket
in the script and in the `-bucket=` flag of the compose file, run the script (it restarts SeaweedFS when identities or rights changed, `--no-restart` skips that). `--regenerate-s3`
replaces all keys
* Deploy the seaweedfs project with `deploy.sh seaweedfs`, then run the script again to create the buckets
* The keys of `backrest`, `offsite-sync` and `vault` are written into the `override.env` files by the script. Copy the keys of `databasus`, `pelican` and `netbird` from `/root/backup-credentials.env` into their settings, then delete the file
* `Write` includes deleting objects in SeaweedFS, so a leaked `backrest` key can delete the local backups. pCloud keeps deleted files (`Backups-deleted`)
* The project runs `weed mini` (the default command of the image, all components in one process) and creates the buckets `backups`, `databases`, `vault`, `pelican` and `netbird` on start (`-bucket=`)
* Only the S3 port `8333` is published. The filer (`8888`) and the admin UI (`23646`) have no authentication and are not exposed

=== Setup Pelican S3 backups

Pelican can store the backups of its servers in an S3. The bucket `pelican` and the identity `pelican` (Read, Write, List
on this bucket only) are created by the setup script. Settings for Pelican, the names of the fields may differ in your version:

* Backup driver S3 in the admin settings (Backups), endpoint `http://100.67.0.1:8333` (the NetBird address of `docker01`), bucket `pelican`,
path-style on, any region (e.g. `us-east-1`)
* Access key and secret of the identity `pelican`, without spaces or quotes (the password manager of the browser may fill them into a wrong field):
`jq -r '.identities[] | select(.name=="pelican") | .credentials[0]' /root/docker/seaweedfs-s3.json`
* Why the IP: the endpoint must be reachable from the Panel and the Wings (containers in Docker networks), and for downloads from the browser (the
Panel hands out presigned URLs). Containers do not know `host.docker.internal` there and cannot resolve `docker01.vpn.rjst.de` (the host DNS is the
NetBird resolver), an IP works for both. The browser must be in the NetBird network.
* The firewall must let the Docker networks reach port 8333 (the rule of the Ansible role `firewall` for `172.16.0.0/12` covers the
destination `100.67.0.1`, see <<Firewall>>). Test it from the networks of the Wings and the Panel, `open` is the right answer:
+
----
docker run --rm --network wings0 alpine nc -zv -w 5 100.67.0.1 8333
docker run --rm --network pelicanpanel_default alpine nc -zv -w 5 100.67.0.1 8333
----
* Test a backup of a server, the download and a restore on a test server. Set the number of backups per server in Pelican, every backup is a
full archive

What this covers and what not: the S3 backups are the backups of the game *servers*. Pelican writes them as plain `.tar.gz`
archives into the bucket `pelican`, restic is not involved. They are *not encrypted*: readable without a password in the S3 and,
after the nightly sync, in pCloud (`Backups/s3/pelican/`, deleted or overwritten archives stay 30 days in `Backups-deleted`).
This is intended, the game server data is not put into a restic repository. Every backup is a full archive (no deduplication),
so set the number of backups per server and the schedule in Pelican to what the storage and the upload can take.

The Panel itself is deliberately not backed up. Its database is SQLite (not MariaDB) in the Docker volume `pelican_panel_data`, it holds
only the configuration of users, nodes and servers and can be set up again. The Wings configuration (`/etc/pelican`, node token) is
created again with the node. The server files in `/var/lib/pelican` are left out as well, the S3 backups cover them.

Because the backups are plain archives, they can be restored without the Panel: download the `.tar.gz` of the server from the S3 or
from pCloud (`Backups/s3/pelican/`) and unpack it into the data directory of the server.

=== Setup NetBird backup

The self-hosted NetBird server runs as a Docker Compose project on `docker01` (default `/opt/netbird`). The scripts in
`scripts/netbird/` back it up, restore it and upgrade it with a rollback point:

* `netbird_backup.sh`: stops NetBird for a moment, copies the config files, `/var/lib/netbird` (SQLite store and keys),
CrowdSec data and certificates, starts NetBird again (also on errors), writes everything with restic to the
repository `netbird/restic` on the local SeaweedFS S3 and applies the retention (8 weekly, 6 monthly). It runs monthly (1st, 00:00) and before every upgrade (`netbird_upgrade.sh`, tag `pre-upgrade`), so up to a month of changes is lost on a restore. A failed
run is reported to Discord (`DISCORD_WEBHOOK_URL`). A PostgreSQL or MySQL store would have to be backed up separately
* `netbird_restore.sh`, `netbird_upgrade.sh` (creates a pre-upgrade backup and a local rollback point), `netbird_rollback.sh`
* `netbird_backup_setup.sh` installs them to `/usr/local/bin`, writes `/etc/netbird-backup.cred` and a cron job

Set it up on `docker01`, the S3 is reached on `127.0.0.1:8333`, no NetBird is involved:

. Add the identity and bucket `netbird`: run `scripts/docker/setup-backup-host.sh` (it restarts SeaweedFS itself and creates the bucket). The keys
  `NETBIRD_ACCESS_KEY_ID` and `NETBIRD_SECRET_ACCESS_KEY` are in `/root/backup-credentials.env`
. Create a Discord webhook for the alerts, see <<Discord alerts>>
. Run the setup (installs restic if missing, asks for the S3 keys and the restic password, initialises the repository):
+
----
cd scripts/netbird
sudo ./netbird_backup_setup.sh --discord-webhook <webhook url> --run
----
. The restic password is in `/root/restic`, store it in your password manager (without it the backups are unreadable)
. Test later with `sudo netbird_backup.sh`. Snapshots from before the move are in `rclone:pCloud:/Backups/netbird`
  (set `RESTIC_REPOSITORY` for `netbird_restore.sh`)

=== Setup Vault backup

Daily at 02:30 UTC (`BACKUP_HOUR`, `BACKUP_MINUTE`) the container fetches the Raft snapshot of Vault
(`sys/storage/raft/snapshot`), writes it with restic to the repository `vault/raft` on the SeaweedFS S3,
applies the retention (`KEEP_*`, default 14 daily, 8 weekly, 12 monthly) and reports a failed run to Discord. It runs in the
host network, so that it uses the NetBird DNS of the host to reach Vault and the S3 on `127.0.0.1`.

* Create the token with `scripts/vault/create-snapshot-token.ps1` (see above). The token is periodic and renewed
by every run, so it stays valid as long as the backup runs at least once per period (32 days)
* Set `VAULT_TOKEN`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` (identity `vault`), `RESTIC_PASSWORD` and optionally `DISCORD_WEBHOOK_URL` in `docker/vault-backup/override.env`
* `docker compose up -d` in the vault-backup folder
* Restore with `scripts/vault/vault_restore.sh`. Snapshots from before the move are in `rclone:pCloud:/Backups/vault_pb`
(set `RESTIC_REPOSITORY`)

== Kubernetes

=== Setup

Each top-level folder is its own independently deployable ArgoCD app-of-apps
(`kube-app-<name>.yaml`), so a domain can be bootstrapped on its own via
`kubectl apply -f kubernetes/kube-app-<name>.yaml`. Inside a domain, the
manifests are split by *how* they are deployed:

----
kubernetes/<domain>/
  apps.yaml     the two child Applications below (the root app only reads this file)
  helm/         Applications that wrap Helm charts (operators, apps) - synced first, wave 0
  kubectl/      raw manifests (custom resources, Gateways, Secrets, ...) - synced second, wave 1
----

`<domain>-kubectl` waits until `<domain>-helm` is healthy, so operators and
their CRDs exist before the custom resources that need them - that is the
enforced ordering, no dry-run workarounds needed. Both are plain directory
sources without AVP; the `<path:...>` values in a Helm app are resolved later,
by the AVP Helm plugin of each child Application. Two rules follow from this:
a Helm app must not depend on anything that lives in the same domain's
`kubectl/` folder (it runs first), and a domain without Helm apps (`spring`)
simply has no `helm/` folder.

. infra (cert-manager, ClusterIssuer, Istio security policies, NetBird operator)
. monitoring (Prometheus, exporters, Istio dashboards)
. cicd (Harbor, Artifactory, Jenkins)
. management (Portal)
. kafka (Strimzi, Apicurio Registry, AKHQ)
. spring

`kube-vault.yaml` (Vault itself) and `kube-app-secrets.yaml` (the
`secrets/` folder: every raw Secret that AVP fills from Vault) sit at the
top level, not inside a domain folder, and are applied standalone before
`infra` — see the Deployment Guide below for why.

Sync-wave annotations (`argocd.argoproj.io/sync-wave`) additionally order
resources *within* `helm/` and within `kubectl/` (e.g. ClusterIssuer before
the NetworkResources), but not across domains — those orderings are
manual/documented instead:
`infra` must be healthy before the others (they all rely on its
ClusterIssuer and cert-manager). Istio itself and ArgoCD's own
installation are deliberately kept outside of GitOps (`istioctl` /
`helm install` per above), since both carry too much blast radius for
automated sync.

=== Deployment Guide

==== 0. Prerequisites (outside of GitOps, done once manually)

. Kubernetes cluster reachable, `kubectl`/`helm` configured against it.
. Istio installed via `istioctl` (base + istiod + ingressgateway) — still
  needed for the remaining public apps (`keycloak.rjst.de`, `microcks.rjst.de`,
  `rjst.de`).
. NetBird self-hosted server running (per the
  https://docs.netbird.io/selfhosted/selfhosted-quickstart[quickstart script]),
  reachable at `proxy.rjst.de`, with its own Traefik reverse proxy.
. A NetBird personal access token (Management API scope) for the Kubernetes
  operator.


==== 1. Bootstrap ArgoCD

----
helm repo add argo https://argoproj.github.io/argo-helm
helm install argocd argo/argo-cd -n argocd --values argocd-values.yaml --create-namespace

# later, to apply changes to argocd-values.yaml:
helm upgrade argocd argo/argo-cd -n argocd --values argocd-values.yaml
----

==== 2. Deploy Vault standalone

----
kubectl apply -f kubernetes/kube-vault.yaml
----

Vault is deliberately *not* part of a domain app: everything that needs
AVP depends on Vault being up, unsealed and populated, so Vault is deployed
on its own first and populated (next step) before any Secret is rendered.

==== 3. Populate Vault secrets

The `avp-helm`/`avp` ArgoCD CMP plugins read secrets from Vault at sync time —
if a path is missing, that Application's manifests simply fail to render.
Populate these *before* applying the `secrets` app in step 4 (paths are
Vault KV v2, under `argocd/data/...`).

Three PowerShell scripts in `scripts/vault/` automate this against the Vault
from step 2 (port-forward it first: `kubectl port-forward -n vault svc/vault 8200:8200`):

----
# One-time only, right after step 2 deploys a fresh, uninitialized Vault:
.\scripts\vault\init-vault.ps1 -VaultAddr http://127.0.0.1:8200

# Generates the app-internal passwords, and prompts for the values that
# can't be generated (Hetzner/NetBird tokens, docker01 DB credentials).
# Safe to re-run - blank answers never overwrite
# existing data. Writes nothing to disk.
.\scripts\vault\generate-secrets.ps1 -VaultAddr http://127.0.0.1:8200 -VaultToken <root-token-from-init>
----

|`argocd/data/hetzner`
|`token` (Hetzner Cloud API token, DNS read/write)

|`argocd/data/netbird`
|`api_key` (NetBird Management API personal access token)

|`argocd/data/prometheus`
|`password` (Grafana admin password)

|`argocd/data/harbor`

(bypassing AVP for that one bootstrap secret). The root token and unseal
keys are only printed to the console, once - it waits for Enter so you can
copy them into your password manager. They are not saved anywhere else.

===== Kubernetes auth (required)

Run `scripts/vault/configure-vault-auth.ps1` once, after `init-vault.ps1`
(it needs `kubectl` against the cluster and a Vault token with admin rights,
e.g. the root token from init). It sets up everything that lets workloads
authenticate to Vault directly with their own ServiceAccount:

* Enables Vault's `kubernetes` auth method and configures it for this cluster.
* Creates the `argocd`, `jenkins`, `dev` and `prod` KV v2 engines.
* Writes the policies and auth roles for ArgoCD, Jenkins, the Spring apps
  (`dev`/`prod` namespaces).

The `argocd` role matters most: ArgoCD's AVP plugin itself logs in to Vault
through it (`AVP_AUTH_TYPE=k8s`, role `argocd`, see `argocd-values.yaml`), so
nothing that uses AVP - including the `secrets` app - renders without it.

Jenkins and Spring don't read from Vault at runtime yet;
wiring them up (Vault Agent injector, Spring Cloud Vault, etc.) is a separate,
later step, app by app.

----
.\scripts\vault\configure-vault-auth.ps1 -VaultAddr http://127.0.0.1:8200 -VaultToken <token>
----

Vault reaches the API server through `https://kubernetes.default.svc:443` (parameter `-KubernetesHost`), not through the
address in your kubeconfig, so a new server IP does not break the login. The script is safe to re-run.

===== Vault backups

Vault is backed up from the Docker host, not from Kubernetes: see *Docker > Setup Vault backup*. It uses a
periodic token with the policy `vault_snapshot` (created by `scripts/vault/create-snapshot-token.ps1`) and does
not depend on anything inside the cluster.

==== 4. Deploy the secrets, then the domains, in this order

----
kubectl apply -f kubernetes/kube-app-secrets.yaml     # 0. renders the Secrets from Vault via AVP, must be healthy before infra
kubectl apply -f kubernetes/kube-app-infra.yaml       # 1. cert-manager, ClusterIssuer, NetBird operator
kubectl apply -f kubernetes/kube-app-monitoring.yaml  # 2. needed before kafka (PodMonitor CRDs)
kubectl apply -f kubernetes/kube-app-cicd.yaml        # 3.
kubectl apply -f kubernetes/kube-app-kafka.yaml       # 4. onwards: order doesn't matter, all only need infra
kubectl apply -f kubernetes/kube-app-management.yaml
kubectl apply -f kubernetes/kube-app-spring.yaml
----

Microcks, Backstage and Keycloak are parked in `kubernetes/parked/<name>/` and not deployed. Each is its own
domain (Microcks with its own MongoDB inside the chart, no Vault secret needed; Backstage pulls its image
from Harbor, so `cicd` has to be healthy first). To deploy or remove one, once `infra` is healthy:

----
kubectl apply -f kubernetes/parked/microcks/kube-app-microcks.yaml
kubectl delete -f kubernetes/parked/microcks/kube-app-microcks.yaml
----

The same with `backstage` or `keycloak` instead of `microcks`.

Why the secrets are a separate app that comes first: some Helm apps need
their Secret at start (the NetBird operator needs `netbird-mgmt-api-key`),
but `helm/` runs before `kubectl/`, so those Secrets can't wait for the
domain's `kubectl/` folder. `secrets` holds them (plus the namespaces they live
in) and is the only place that runs the AVP plugin, so *every* Secret that is
filled from Vault lives there. Don't set the plugin on an app whose files
contain no `<path` / `avp.kubernetes.io` marker: the plugin's discovery check
finds nothing and ArgoCD fails with "could not find cmp-server plugin".
Never put the AVP plugin on a `helm/` app: it would resolve every `<path:...>` in the child Applications'
`HELM_VALUES` and write those passwords in plain text into the Application
objects.

Watch `infra` reach Healthy in the ArgoCD UI/CLI before applying the rest —
nothing else will work without its ClusterIssuer and cert-manager.

==== 5. NetBird configuration

What lives in Git, and what doesn't:

* *In Git, via the NetBird operator*: the groups. `k8s-admins` (peers that may
  reach every app) and `kubernetes-services` (every `NetworkResource` is in it)
  live in `kubernetes/infra/kubectl/kube-netbird-access.yaml`, together with the
  groups of the apps deployed with `infra` (Vault, ArgoCD). Every other app
  declares its own destination group `k8s-<app>` and user group `<app>-users`
  next to its `NetworkResource`, so they exist only while that app's domain is
  deployed. Removing a domain deletes them again - delete the policy that uses
  them (and the zone's distribution-group entry) first, NetBird refuses to
  delete a group that is still referenced.
* *By hand in the dashboard*:
  . `DNS > Zones > Add Zone`: name and domain `k8sdev.rjst.de` (a separate internal
    zone: `proxy.rjst.de` is the NetBird host's own public domain and must not
    be shadowed; a subdomain of `rjst.de` so Let's Encrypt DNS-01 can issue for
    it). *Distribution Groups*: `k8s-admins` and every `<app>-users` (only peers
    in these groups resolve the records; the zone is not a security boundary,
    the policies are). The zone must exist before the `NetworkRouter` syncs.
  . Records in that zone: the operator creates `<service>.<namespace>.k8sdev.rjst.de`
    for every `NetworkResource`. Add a CNAME per app to that name, e.g.
    `vault.k8sdev.rjst.de` -> `gw-vault.istio-internal.k8sdev.rjst.de`.
  . `Access Control > Policies`, all TCP 443, one-way:
    `k8s-admins` -> `kubernetes-services` (every app), and per app
    `<app>-users` -> `k8s-<app>` (e.g. `vault-users` -> `k8s-vault`).
    NetBird is deny-by-default and the operator writes no policies (its
    `NBPolicy` resource creates nothing for `NetworkResource`s, so it is
    deliberately not used).
  . `Peers`: put each peer/user into `k8s-admins` and/or the matching
    `<app>-users`. Nothing is reachable until a peer is in a group with a policy.
* Guide this follows: https://docs.netbird.io/use-cases/kubernetes/route-to-a-kubernetes-service[Route to a Kubernetes service].
  The router runs a single routing peer (`workloadOverride.replicas: 1`,
  single-node cluster); raise it to 3+ for failover.

Every app is reached as `https://<app>.k8sdev.rjst.de` (see the next section):
its own Gateway, Service, VirtualService and `NetworkResource` live next to the
app (`kube-gw-argocd.yaml` in `infra`, the others in their domain's `kubectl/`
folder) and create the record `gw-<app>.istio-internal.k8sdev.rjst.de`.

===== HTTPS entry for internal apps (`istio-internal`)

Apps are reached as `https://<app>.k8sdev.rjst.de` (port 443, Let's Encrypt
wildcard `*.k8sdev.rjst.de` via the `letsencrypt` ClusterIssuer, DNS-01 at
Hetzner). `istio-internal-gateway` (`infra/helm`) is a second Istio ingress
gateway, ClusterIP only - unlike the public `istio-ingressgateway`, nothing
outside the cluster can reach it except through the NetBird routing peer.
NetBird separates access per destination, not per hostname, so every app gets
its own Service, its own listener port on the gateway and its own
`NetworkResource` (`infra/kubectl/kube-istio-internal.yaml`). Each listener
only accepts that app's hostname, so per-app groups stay meaningful.

===== Portal (list of all apps and services)

`management/kubectl/portal.yaml` serves `https://portal.k8sdev.rjst.de`, a page with a
link to every app and service. Nothing is listed by hand; a sidecar rebuilds the list
every minute:

* *Kubernetes*: every Istio `VirtualService` (`https://<first host>`). A new app shows up
  as soon as its `VirtualService` is synced. Optional annotations on the
  `VirtualService` set the card: `portal.rjst.de/name`, `/group`, `/description`,
  `/icon` (a https://devicon.dev[Devicon] name like `argocd` or `jenkins/plain`; other text,
  e.g. an emoji, is shown as is) and `/hidden: "true"` to leave it out. Without them the card is
  named after the first part of the host.
  A `VirtualService` in one of the stage namespaces (`STAGE_NAMESPACES` in the Deployment,
  default `dev,test,stage,prod`) is shown as an app with a stage: one card per app (name from
  the `app` label), one link per stage with the version (`app.kubernetes.io/version`).
  `/stage` and `/version` set them explicitly for other namespaces.
* *Docker*: every service in `docker/*/docker-compose.yml` that has the labels `portal.name`
  and `portal.url` (the NetBird reverse proxy address, `https://<app>.proxy.rjst.de`).
  Optional: `portal.group`, `portal.description`, `portal.icon` (Devicon name). The list comes from the Git
  repository (`master`), so a service appears once it is merged, not once its container runs.
* *Static*: services that are neither a `VirtualService` nor in `docker/` (NetBird on its own
  host) are listed in the `STATIC_SERVICES` env var of the generator container, a JSON list of
  `{name, url, group, description, icon}`.

Needs the usual NetBird steps by hand: a CNAME `portal` in the zone and the policy
`portal-users` -> `k8s-portal` on TCP 443.

===== kubectl through NetBird (API server proxy)

`infra/kubectl/kube-netbird-apiproxy.yaml` deploys the operator's `ClusterProxy` `k8sdev`
(https://docs.netbird.io/use-cases/kubernetes/api-server-proxy). The proxy pod is a NetBird peer
in the group `k8s-api-proxy`; it forwards `kubectl` requests to the API server and impersonates
the caller: the Kubernetes user is the NetBird user, the Kubernetes groups are the NetBird
groups the *user* belongs to. No credentials in a kubeconfig.

What may be done is decided by RBAC. Only one binding exists so far: the NetBird group
`k8s-cluster-admins` is bound to `cluster-admin`.

By hand in the dashboard:

. `Team > Users > <your user> > Auto-assigned groups`: add `k8s-cluster-admins`. The *user* has
  to be in the group; the membership of your devices (peers) does not count.
. `Access Control > Policies`: `k8s-cluster-admins` -> `k8s-api-proxy` (find the port in the
  proxy pod, `kubectl -n netbird get pods`, the operator docs do not name it).

Then on your machine (NetBird CLI >= 0.79):

----
netbird kubernetes list
netbird kubernetes write-kubeconfig k8sdev
kubectl --context k8sdev get pods -A
----

The proxy service account may impersonate any user and group, so the proxy pod is as sensitive as
`cluster-admin`.
